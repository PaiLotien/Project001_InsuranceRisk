# MLflow / SHAP 模型能力评估

## 结论

当前系统的核心链路是：

```text
Excel → 字段规范化 → YAML 规则引擎 → 预警等级 → 归因说明 → 邮件通知
```

它还不是训练型机器学习系统。当前上传表中的 `预警等级` 会被规则引擎重新计算，不能直接当作独立人工标签；如果拿这个结果训练模型，模型学到的只是现有规则，不能证明发现了新的风险规律。

因此本阶段的决策是：

| 能力 | 当前是否接入 | 判断 |
|---|---:|---|
| 数据漂移监测 | 是 | 先使用本项目内置的 PSI、缺失率和类别分布监测，依赖少、解释清楚 |
| MLflow | 否 | 等出现第一个可复现实验、时间切分验证和候选模型后再接入 |
| SHAP | 否 | 等训练模型和可信标签成立后再解释模型，不解释规则引擎 |
| Evidently | 暂不作为运行依赖 | 当前自研漂移结果已覆盖 MVP 需求，后续需要报告、仪表盘或更多统计检验时再引入 |

## 为什么 SHAP 现在不适合直接接入

SHAP 的输入前提是一个已经训练好的预测模型，以及该模型真正使用的特征。当前项目缺少：

1. 可追溯的人工审核标签或真实结果标签；
2. 明确的预测目标，例如“未来 7 天是否超过预期成本率阈值”；
3. 按时间切分的训练集、验证集和测试集；
4. 防止同一机构/车型跨时间泄漏的样本设计；
5. 与业务规则结果对照的基线指标。

后续若建立 `高风险事件 = 下一期真实成本率超过阈值` 这样的标签，再用树模型做基线，SHAP 才能回答“模型为什么把这一行判为高风险”。否则展示的 SHAP 值容易被误读成“业务归因”。

## 为什么 MLflow 现在不必急着加入

MLflow 的价值在于跟踪参数、指标、数据版本、模型产物和模型注册，而不是替代训练算法。当前没有模型训练任务，接入后只能记录空实验，反而会增加部署和依赖成本。

推荐的接入顺序：

1. 先固定特征字典、标签定义和时间切分规则；
2. 用一个简单的 Logistic Regression 或 Random Forest 建立可解释基线；
3. 记录 AUCPR、召回率、精确率、校准误差和业务漏报成本；
4. 再用 MLflow Tracking 保存参数、指标和数据快照摘要；
5. 候选模型通过业务验收后，再使用 Model Registry 管理版本；
6. 最后接 SHAP，输出全局重要性和单条记录局部解释。

## 当前漂移监测口径

代码位置：`src/monitoring/drift.py`。

- 数值字段：`预期成本率`、`保费占比`、`签单保费_万元` 使用 PSI；
- 类别字段：`机构`、`车型`、`预警等级` 使用类别分布 PSI；
- 额外监测基准缺失率、当前缺失率和均值变化；
- PSI `< 0.10` 为稳定，`0.10–0.25` 为关注，`≥ 0.25` 为漂移；
- 任一数据集少于 20 行时显示“样本不足”，不强行下结论；
- 漂移结果只提示数据分布变化，不改变预警等级，也不替代业务规则校验。

漂移监测需要至少一个不同日期的历史快照。核心指标页中的“保存当前快照”会保存趋势字段到本地 `.irds/history`，该目录已被 Git 忽略。

## 外部能力参考

- [MLflow Model Registry](https://github.com/mlflow/mlflow/blob/master/docs/docs/classic-ml/model-registry/index.mdx)：模型版本、血缘、别名、标签与生命周期管理。
- [SHAP](https://github.com/shap/shap)：解释已经训练好的机器学习模型，树模型有专门的高效解释器。
- [Evidently](https://github.com/evidentlyai/evidently)：覆盖数据漂移、模型评估和线上监测的更完整工具链。

## 当前风险边界

本项目目前可以诚实地称为“规则驱动的车险风险监控 Demo”，不能称为已完成的机器学习预测系统。只有真实业务数据、稳定标签、时间外测试和业务验收都具备后，才进入模型训练与注册阶段。
